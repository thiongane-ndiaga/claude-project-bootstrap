# Location and format of ADRs

## Status

Proposed.

## Context

Archgate stores its ADRs in `.archgate/adrs/` by default. The project wants its architecture documentation grouped under `docs/architecture/` (ARCH-001). Archgate has no status field in its frontmatter, and `archgate adr create --rules` (v0.61.0) writes `rules: false` while it creates the `.rules.ts` file.

## Decision

- ADRs live in `docs/architecture/adrs/`, configured by `paths.adrs` in `.archgate/config.json`. The `.archgate/` folder stays: it is used to locate the project root.
- Files follow `<PREFIX>-NNN-<slug>.md`, with a companion `<PREFIX>-NNN-<slug>.rules.ts` when `rules: true`.
- The frontmatter contains `id`, `title`, `domain` and `rules`; the `id` reuses the prefix of the file name.
- The status is in the body, under `## Status`, and starts with **Proposed**, **Accepted**, **Rejected**, **Superseded** or **Obsolete**.
- ADRs are created with `archgate adr create`, with rules only if they can be verified.

## Do's and Don'ts

### Do

- Check that `rules:` matches the presence of the `.rules.ts` after an `adr create --rules`.
- Name in `## Status` the issue that carries the decision.

### Don't

- Do not edit `docs/architecture/rules.d.ts` or `.archgate/rules.d.ts`: they are regenerated by Archgate and ignored by git.

## Consequences

### Positive

- All the architecture documentation is in one place.
- The CLI's default is detected automatically.

### Negative

- Non-standard path: the Archgate plugin's skills sometimes assume `.archgate/adrs/`.

### Risks

- An Archgate update changes the behavior of `paths.adrs`: `archgate adr list` and the CI would reveal it.

## Compliance and Enforcement

`ARCH-003-emplacement-et-format-des-adr.rules.ts` checks, for each ADR: file name, consistent `id`, `domain` present, `rules:` ⇔ `.rules.ts` match, and a `## Status` section with an allowed value. It also reports any ADR left in `.archgate/adrs/`.
