## Contexte

La convention « issue » est encodée dans une vingtaine de modèles (français et anglais) : `CLAUDE.md`, `docs/workflow.md`, gabarit de PR, `traceability-checker` (avec `legacy-agents`), profils (`business-analyst`, `project-lead`, `product-owner`, skills `pr-readiness-review` et `spec-review`), `spec-reviewer` (module `openspec`), `openspec-config.md`, ADR ARCH-002/003/004/005. Le moteur de blocs ne connaît que le OU (`a|b`) et l'imbrication (ET), pas la négation. Le moteur de modules dérive des pseudo-modules de la configuration et hérite des clés lors de `--update` (précédents : `advisor`, `sonar`). Comme `sonar`, le changement touche `scaffold.mjs`, `catalog.mjs`, `state.mjs` et des modèles hors de son dossier (ARCH-010 le reconnaît pour les clés de configuration).

## Décisions

- **D1. Source au choix par projet.** `jiraSource` vaut `github` ou `jira`. Absente, elle équivaut à `github` ; une valeur donnée, même `github`, est consignée au manifeste (comme `sonar`).
- **D2. Deux clés, module obligatoire.** `jira` (clé de projet `[A-Z][A-Z0-9]{1,9}`, choix assumé : le tiret bas est exclu, comme les majuscules le sont des id OpenSpec) et `jiraSource` sont refusées sans le module `jira` (code 1), héritées par `--update`, retirées par `null`. Retirer le module alors que l'une est héritée échoue. Sans clé `jira`, le contrôle accepte toute clé `[A-Z][A-Z0-9]+-N`, au risque de faux positifs (`UTF-8`, `SHA-256`) : `docs/jira.md` recommande de fixer la clé.
- **D3. Deux pseudo-modules complémentaires**, déclarés dans `catalog.mjs` : `jira-source` (actif quand `jiraSource` vaut `jira`) et `issue-source` (actif sinon, y compris sans le module, pour que les textes actuels `Closes #N` restent inchangés). Paramètres : `JIRA_KEY_RE` (clé du projet ou motif générique) et `JIRA_KEY_EXAMPLE` (`ABC-123` avec la clé, sinon `<CLE>-123` / `<KEY>-123` selon la langue, via `LANG_PARAMS`).
- **D4. Contrôle `scripts/check-jira-key.mjs`**, étape du job `pr-title` de `ci.yml` après `check-pr-title` et avec `if: ${{ !cancelled() }}` pour que l'auteur voie les deux erreurs d'un coup. `PR_TITLE: ${{ github.event.pull_request.title }}` et `HEAD_REF: ${{ github.head_ref }}` passent par l'environnement, jamais interpolés dans le shell (ARCH-004). Le job ne tourne que sur `pull_request` : `edited` relance le contrôle quand on corrige le titre. Une branche mal nommée ne se renomme pas sur une PR ouverte : il faut une nouvelle PR (dit dans `docs/jira.md`). `HEAD_REF` vide (exécution locale) : la clé doit alors figurer dans le titre. La clé est cherchée comme mot entier (`XABC-12` ne valide pas `ABC-12`). Exemptions : `dependabot/` et `release-please--`.
- **D5. Titre de PR.** Le scope de `check-pr-title.mjs` reste `[a-z0-9-]+` : la clé va dans la description (`feat(import): ABC-12 accept monthly lines`), pas dans le scope. Le message d'erreur et `docs/jira.md` le disent.
- **D6. Conventions en `jira`.** Branche `<type>/<CLE-N>-<slug>` (majuscules, `feat/ABC-12-import`), id OpenSpec en minuscules `<cle-n>-<slug>` (`abc-12-import`, car OpenSpec refuse les majuscules ; dossier archivé `<date>-abc-12-import`), en-tête de `proposal.md` `Ticket: ABC-12` au lieu de `Issue: #N`, corps de PR `Refs ABC-12` au lieu de `Closes #N` (le ticket se ferme dans Jira). Phase 4 du skill : branche `docs/<CLE-N>-accept-tooling-adrs`.
- **D7. Fichiers à variantes** (blocs `jira-source` / `issue-source`, `templates` et `templates.en`) : gabarit de PR, `docs/workflow.md` (tableau des conventions, ligne « l'issue se ferme », exception Dependabot, tables de contrôles, ligne « Double encodage » de `check-jira-key.mjs`), `CLAUDE.md` (pointeur vers la table de lecture), `traceability-checker`, skills `pr-readiness-review` et `spec-review`, agent `spec-reviewer`, `openspec-config.md`, ARCH-002, ARCH-003, ARCH-005. En `jira`, `spec-review` et `spec-reviewer` demandent le texte du ticket à l'utilisateur ou dans `proposal.md` (`gh issue view` ne lit pas Jira). Le champ « Clé Jira » (facultatif) s'ajoute à `feature.yml`, `bug.yml` et `architecture-decision.yml` en mode `issue-source` avec le module.
- **D8. Table de lecture** de `docs/jira.md` (mode `jira`) pour la prose restante : issue → ticket, `#N` → `CLE-N`, `Closes #N` → `Refs CLE-N`, `Issue: #N` → `Ticket: CLE-N`, `gh issue view/list/create` → Jira, non accessible aux agents, formulaire Décision d'architecture → ticket Jira, profil `product-owner` à utiliser sans `gh issue create`. `CLAUDE.md` renvoie à elle. La prose des profils et ARCH-004 n'est pas réécrite.
- **D9. Module `projects`** : proposé à la désactivation en phase 0, jamais forcé. Les « Autolink references » du dépôt (préfixe `ABC-` vers l'URL Jira) et la fermeture des tickets sont des étapes manuelles de `docs/jira.md`.
- **D10. Reprise de session.** `state.mjs` (`ANSWER_KEYS`) gagne `jira`, `jiraSource` et `sonar`, absent jusqu'ici.
- **D11. ADR.** ARCH-017 (plugin) documente la source du besoin ; ARCH-005 est amendé dans le plugin (le plugin reste en mode GitHub : l'amendement décrit ce que le module génère) et dans le modèle.

## Hors périmètre

Transition automatique des tickets, synchronisation d'issues, plugin Archgate propre à Jira, réécriture de la prose des profils, étape Jira dans le `Jenkinsfile` du module `jenkins` (le contrôle ne tourne que dans `ci.yml`), passage `github` → `jira` d'un projet qui a déjà des changements `<N>-<slug>` en cours.

## Risques

- Aucun essai réel avec une instance Jira : documenté comme non observé.
- En mode `jira`, des textes disent encore « issue » : la table de lecture le compense, au prix d'une lecture indirecte.
